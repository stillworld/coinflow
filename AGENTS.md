# RuneLite Plugin Development — Agent Guidelines

## Architecture & Codebase Map

### Data & Execution Flow
`Game Events / Ticks` ➔ `InterfaceTracker` (suppress false diffs if bank/GE/trade open; flag shop-open state) ➔ `InventorySnapshotService` (compute tick-to-tick item diffs) ➔ `InventoryReconciliationEngine` (evaluates diff against handler chain; `ShopTracker` handles diffs while a shop is open) ➔ `CoinFlowSession` (updates net GP, profit/loss rates, goals) ➔ `CoinFlowOverlay` / `CoinFlowGoldDropOverlay` / `CoinFlowPanel` (UI & HUD updates).

### Core Components (`src/main/java/com/coinflow/`)
- `CoinFlowPlugin.java`: Lifecycle entry point (`startUp`/`shutDown`), event subscribers (`@Subscribe`), overlay/panel manager. Subscribers stay here but delegate to focused package-private helpers that share the plugin's cross-tick state via a `CoinFlowPlugin` reference: `SessionLifecycleManager` (startup/shutdown, game-state & config transitions, baselines, resets, account-identity isolation via `AccountHashChanged`/`checkAccount` — a hash change resets session, GE basis, death ledger and cannon state so one account's bookkeeping can never book against another's; also owns `OverlayMenuClicked` handling for the HUD overlay's `RUNELITE_OVERLAY` entries (`Reset` → instant `resetSession`, `View Summary` → opens the session summary — `RUNELITE_OVERLAY_CONFIG`/`Configure` stays client-handled) plus the item-row `ignoreItem`/`removeSessionItem` session mutations marshalled to the client thread), `InventoryDiffProcessor` (`ItemContainerChanged`/`VarbitChanged`, `processInventoryChanges`, `stripNonEconomicItems`), `GameTickProcessor` (`onGameTick` ordering — grace windows, pickup drains, death settle, worn-ammo/Barrows-wear/weapon-charge expenses, session tick; re-evaluates the world type every tick and freezes the session clock + diffs while on unsupported worlds (Leagues, Deadman, Beta, Tournament, seasonal), re-baselining on return so transition diffs never book), `MenuIntentHandler` (`MenuOptionClicked` intents — drop intents, container/charged-item re-baselines, and `Open`/`Loot`/`Search` CC_OP clicks on non-container inventory items recorded as pack-open intents), `ChatMessageHandler` + `ChatMessageParser` (chat triggers; regex/item-name parsing), `ContainerPickupTracker` (Take clicks, looting-bag/gem-bag/herb-sack pending pickups, PvP key chests, despawn matching), `CannonTracker` (deployed dwarf-cannon parts and loaded-balls bookkeeping), `BlastFurnaceTracker` (furnace presence via conveyor spawn events, coffer deposits/withdrawals/drain, dispenser-rescue ledger), `DeathFlowCoordinator` (death settle/recovery orchestration), `SessionApplier` (`processGains*`/`applyGeLedger`, ignored-item filter, goal notify), `GoalTracker` (per-account persisted goal progress + completion flag under `goalProgress.<accountHash>` — `"<goalAmount>|<persistedGp>|<complete>|<trackedSeconds>"`, the seconds field absent on pre-existing values and reading as 0, self-invalidating when the configured amount changes; `persistSession` checkpoints the session's contribution + tracked time (the `includeAfkTime` clock) at reset/logout/shutdown plus a ~60-second tick checkpoint in `GameTickProcessor` so a crash loses at most that window, and is idempotent via per-session offsets cleared by `onNewSession` at every session replacement; `goalDisplayTotal()`/`goalDisplaySeconds()` on the plugin fold persisted progress/time into the live contribution for UI and notification — complete goals freeze at "Goal Reached!" until cleared or re-targeted, and toggling `trackSpent` mid-goal mixes net/gross bases), `ActivityMonitor` (activity/idle, animation/graphic tracking; also `classify(session, tick)` — the activity classifier feeding `ActivityTimeline`: AFK > Banking/GE widgets > combat NPC target + recent combat XP > Blast Furnace > most-recent skilling XP (a Magic-XP + recent-`LOADING` conjunction — `onSceneLoad` tick ≤ `TELEPORT_SIGNAL_TICKS` 10 — reclassifies as `TELEPORT` since a spellbook teleport's only XP tell is the Magic drop; item teleports grant no XP and stay unclassified), maintaining a rolling 50-tick deque of NPC target names for the combat label; like core `XpTrackerPlugin`, `StatChanged` is ignored for 2 game ticks after `LOGGING_IN`/`HOPPING` — the server's login XP sync would otherwise read as a same-tick gain in every skill and open a phantom skilling segment — and `previousSkillXp` is re-seeded from the client when the window closes), `ActionClassifiers` (static action/animation checks — `isContainerOrChargedItemTarget` excludes `coin pouch`, which converts to coins in place and is not a storage container). Package-private fields and wrapper methods on the plugin are the test-facing API — tests access them directly, so keep the wrappers when moving logic.
- `CoinFlowConfig.java`: Configuration options (`@ConfigGroup("coinflow")`), display toggles (incl. `showSparkline`, default off), goal mode thresholds. Goal progress itself is not a config item — it lives in hidden `goalProgress.<accountHash>` keys written by `GoalTracker`; `onConfigChanged` returns early on these internal writes so checkpoints never rebuild the filter set or spam the log.
- `CoinFlowSession.java`: Active session state; records net GP, gold/hour rates, elapsed time, milestones, goal targets. Goal math also exposes `currentTotal` overloads (`getGoalProgress`/`getGoalRemaining`/`getGoalEtaSeconds`) so callers can fold persisted cross-session progress in; the ETA the UI shows is the blended-rate overload `getGoalEtaSeconds(goalAmount, currentTotal, trackedSeconds)` — remaining GP ÷ (blended progress ÷ blended tracked seconds) — so fresh logins and losing stretches can't spike or blank it. `isSyntheticRowId` is the shared check for synthetic GP-denominated rows (qty = gp, price = 1): `"Death"` (`SKULL`), `"GE Tax"` (`COINS_10000`), `"Blast Furnace coffer"` (`COINS_1000`), `"Barrows wear"` (`BARROWS_INTERFACE_DHAROK`).
- `ActivityTimeline.java`: Per-activity session segmentation. A *sampler*, not hooks: `GameTickProcessor` calls `onTick` after `session.tick` with the session's absolute gross/expense totals and the classified activity, so every booking path is covered without touching mutation sites. A differing `ActivityClass` must persist `CONFIRM_TICKS`=20 (12s; `QUICK_CONFIRM_TICKS`=5 for AFK/BANKING/TELEPORT — teleports are momentary) as `pending` before a new segment opens, seeded with the pending accumulation (back-dated); a sub-confirm candidate or a third-class flip folds back into the live segment. Separately, a short gap (BANKING/AFK/TELEPORT/OTHER ≤ `FOLD_GAP_MAX` 3 min) flanked by the same activity folds into the run on confirm — `[Renu, Bank 1:13, Renu]` stays one segment covering the trip, so bank stops don't spam duplicate rows; longer gaps keep their own row. Kills come from `NpcLootReceived` (core LootManager event, already per-kill deduped) and are attributed to any live/pending COMBAT segment regardless of label (mixed-NPC content like DKs would undercount under label matching). `rebase()` resyncs baselines after user row removals (`removeSessionItem`/`ignoreItem`) so deletions never book as segment losses; `reset()` on session/account reset. Segment list is published as a volatile immutable snapshot each tick — EDT/overlay readers never see mutable state; `revision` bumps only on structural changes so the panel can skip rebuilds.
- `ProfitHistory.java`: Bounded cumulative-profit series for the Session Overview sparkline. Same sampler pattern as `ActivityTimeline`: `GameTickProcessor` calls `onTick(net-or-gross)` right after the timeline sample (always — even with the toggle off — so enabling mid-session shows history); first tick after reset records immediately, then every `BASE_INTERVAL_TICKS` 5. At `CAPACITY` 240 points adjacent pairs are averaged into 120 and the interval doubles, so any session length costs the same memory/paint. A `volatile Snapshot` (`values` copy, `revision`, `min`/`max`) is replaced only on record/downsample/reset — `snapshot()` is a reference read, never allocates. `reset()` is called at every `activityTimeline.reset()` site (`startUp`, `shutDown`, `resetSessionOnClientThread`); the plugin instance is reused across toggles so stale points would otherwise leak. The x-axis is game ticks, not wall-clock — logged-out/unsupported-world time is simply absent, consistent with the session clock; a mid-session `trackSpent` flip steps the curve (accepted for a visual).
- `CoinFlowPanel.java`: Swing sidebar panel; displays session metrics, item transaction breakdown, reset button. The Session Overview card's standard body optionally renders `SparklinePanel` (28px; `showSparkline` config, **default off**) directly under the Net Profit value — a `Path2D` polyline with a faint zero line when the range crosses zero, stroke green/orange by the latest value, flat series drawn at the vertical centre, nothing painted under 2 points; it repaints only when the snapshot `revision` changes, and `updateSessionUI` pushes `plugin.profitHistory.snapshot()` each tick while the panel is parented. Omitted in compact mode and when the card is collapsed; the toggle takes effect live because `onConfigChanged` already rebuilds the session card. The "Profit by Activity" card (between Goal and Item Breakdown; `showTimeline`/`timelineCardCollapsed` config; header tooltip explains its purpose) has a `Timeline`/`Totals` view bar (`timelineTotalsView` — a non-persisted field like `itemFilter`, defaults to Totals): Timeline lists segments newest-first, Totals renders `aggregateByLabel()` (one row per activity, longest first, stint count in the tooltip). Both views share the `RowStats` view model and `buildActivityRow`: a 3px left stripe coloured by `Kind` (combat red, skilling green, Blast Furnace amber, banking blue, teleport violet, AFK/other grey), a 16px icon from `plugin.skillIconManager` (`SkillIconManager`, injected on the plugin rather than the panel constructor so tests keep the 4-arg constructor; trained skill for skilling, Attack for combat, Smithing for Blast Furnace, Magic for Teleport, none for banking/AFK — null-safe in tests), a faint kind-tinted share bar (`ShareBarPanel`) filled to the row's share of session time, and a lighter background marking the live row. Per tick `updateLiveSegmentRow` rewrites every rendered row's labels, tooltip and share in place (`activityRows`, matched by position in Timeline and by kind|label key in Totals, where sort order can shift) — structural rebuilds still happen only on timeline revision/config changes. The one-line detail leads with the most useful figure so tail truncation drops the least: combat shows `duration · kills · net/kill`, other kinds `duration · gp/hr` — gp/hr is omitted for Banking/AFK and for segments under `MIN_RATE_SECONDS` (120s), where hourly extrapolation is noise. Zero-net rows render `0 gp` in neutral grey — except the bootstrap `Other` bucket, which `currentRowStats` hides entirely while zero-net (`isEmptyOther`); `updateLiveSegmentRow` rebuilds the card when the rendered row-set size diverges from the filtered stats so a hidden/revealed `Other` row appears or disappears the tick its net first leaves or returns to zero, and a card whose only segment is a hidden `Other` falls back to the "No activity yet" placeholder. The row tooltip (`activityTooltip`) carries the full breakdown — time (+active), earned, spent, net, rate, kills/hr, per-kill net and supplies; rows rebuild only on `timeline.getRevision()`/config change — per-tick it just `setText`s the retained live-row labels. Shows a "Paused" indicator while tracking is suspended on an unsupported world type. The Item Breakdown card has an `All`/`Loot`/`Spent` filter bar (shown when `trackSpent` is on) and a right-click context menu on each row: `Remove from Session` (drops the row's carried value via `CoinFlowSession.withoutItem`), `Ignore <name>` (normalizes `" (dose)"`/`" (portion)"` rows to their base item via `ConsumableRegistry.canonicalIgnoreName`, appends to `ignoredItems` config, and removes the item from the session — omitted on synthetic `Death`/`GE Tax`/`Blast Furnace coffer`/`Barrows wear` rows, detected by `isSyntheticRow` via `CoinFlowSession.isSyntheticRowId`), and `Open on OSRS Wiki` (`LinkBrowser` + `Special:Lookup?id=`; synthetic rows link to Death/GE-tax/Blast-Furnace/Barrows-equipment wiki pages instead).
- `CoinFlowOverlay.java`: Draggable HUD overlay displaying net profit, GP/hr, and goal progress. The `overlayStyle` config (`Detailed`/`Single Line Gp/hr`/`Single Line Net Profit`) switches to a compact one-line `X gp/hr` or `X gp` display; `showOverlayBackground` toggles the panel background (set `STANDARD_BACKGROUND_COLOR` or `null` each frame — the exact constant is required so RuneLite's global "Overlay Color" substitution still works). Single-line mode renders `panelComponent` directly rather than via `OverlayPanel.render()` so a persisted overlay resize (`getPreferredSize()`) cannot stretch or wrap the line, and calls `setResizable(false)` while active. `compactMode` (the same toggle used by the side panel) tightens the Detailed overlay — 2px panel border, reduced padding/min-width, hidden title row, and switches to `FontManager.getRunescapeSmallFont()` (a distinct compact typeface — deriving a fractional size from the interface font rasterizes poorly; set on `graphics` and restored in a `finally` since components share the Graphics2D font); the non-compact title renders via `FontTitleComponent` — a TitleComponent-style left-aligned row with a `TextComponent` per-component font override — in `runescape_small` so the header sits below the body size (the small font is the smallest distinct typeface, so compact omits the title rather than shrinking past it); the goal bar stays 16px since `ProgressBarComponent` floors its height there; the goal bar uses `TEXT_ONLY` edge labels — goal name on the left (`leftLabel`, hard-capped at `GOAL_BAR_LABEL_MAX_CHARS` 20 via `goalBarName` — `GOAL_BAR_LABEL_MAX_COMPACT` 10 with a `...` suffix in compact mode), `"1.4% - 4:32"` on the right (`rightLabel`); a centered label (e.g. `PERCENTAGE` mode) is deliberately avoided since it paints over a long left label at narrow widths. `maxLineWidth` budgets both edge labels so a long name widens rather than truncates. Right-click menu entries (`OverlayMenuEntry` `RUNELITE_OVERLAY`): `View Summary` and `Reset`, handled in `SessionLifecycleManager.onOverlayMenuClicked` — like all RuneLite overlay menus they only appear on **Shift+right-click** (`OverlayRenderer.onPostMenuSort` gates on `KC_SHIFT`).
- `CoinFlowGoldDropOverlay.java`: Floating canvas overlay showing animated `+GP` / `-GP` drop indicators on changes.
- `InventorySnapshot.java`: Immutable value object capturing inventory/equipment items, quantities, and GE/HA valuations.
- `InventorySnapshotService.java`: Compares tick-over-tick snapshots and emits net item diffs for reconciliation. `takeInventorySnapshot` merges nested-container contents into the inventory map — Rune Pouch runes (live `RUNE_POUCH_TYPE/QUANTITY_*` varbits via the `RUNEPOUCH_RUNE` enum), Looting Bag cache, Scroll Book, Quiver, Sanctifier — so storage transfers net to zero in theory. In practice a pouch transfer splits across an `ItemContainerChanged` and a `VarbitChanged` that can land in either order, and each half diffs as a phantom gain/loss against stale varbits: while a pouch is carried, `InventoryDiffProcessor` defers pouch-eligible rune rows (`isPouchRuneId`) into `pendingPouchDiffs` and settles the net on `GameTick` (`settlePendingPouchDiffs`) once the mirror halves cancel — leftovers are real diffs (spell costs, pickups, drops) routed back through `reconcileAndApplyDiff`; held rows are dropped if suppression begins mid-window since the baseline already absorbed them. A re-baseline taken *mid-transfer* is worse: it swallows one half of the split pair into the new reference, leaving the other half unpaired — when a consumed baseline's diff contains a pouch-rune row, `pouchAbsorbBaselineTick` records it and settle drops held rows for that tick + 1. A deferred Nature rune still flags `context.setAlchemy(true)` so `HighAlchemyHandler` keeps pairing the cast. `isBankOrContainerOpen` also checks the pouch interface's `RunePouch.UNIVERSE` live visibility, so deposits through the open pouch UI baseline even if `WidgetLoaded(190)` never fired. Sailing boat cargo holds (`InventoryID.SAILING_BOAT_1..5_CARGOHOLD`) merge the same way while `VarbitID.SAILING_BOAT_SPAWNED` == 1 — the hold stays spawned (and its container live) while moored at an island or port, so consumption straight out of the hold (landing-site/facility builds, ship-cannon shots) diffs as a real loss; hold `ItemContainerChanged` events route through `processInventoryChanges(inv, cargoHoldDiff=true)` since they produce no INV event, and `context.cargoHoldLoss` makes `ConsumablesAndDropsHandler` expense the loss (no drop path out of the hold) instead of filing it under owned-drop bookkeeping. The `SAILING_BOAT_CARGOHOLD` interface stays suppressed so deposits/withdrawals baseline; the `SAILING_BOAT_SPAWNED` varbit flip schedules a re-baseline + 3-tick grace so spawn/despawn never books the hold's contents.
- `InterfaceTracker.java`: Tracks open widget interfaces (Bank, GE, Trade, Death Storage, Omnishop/PvP stores) to prevent false profit/loss. The standalone GE collection screen (`GE_COLLECT`, group 402 — collect boxes and banker/clerk "Collect") is suppressed alongside `GE_OFFERS`/`GE_OFFERS_SIDE`; purchases collected through it would otherwise arrive as market-value loot since collection fires no suppressed interface and usually no matching 'Collect' intent. The clerk's item-sets exchange (`ITEMSETS`/`ITEMSETS_SIDE`) is suppressed because set↔components conversions would otherwise book the unpacked pieces as phantom profit. Omnishops (`OMNISHOP_MAIN`/`OMNISHOP_SIDE` — points shops like the Mixology rewards store, NMZ imbues, volcanic/fossil stores) stay suppressed for noise, but their currency is varp-based so purchases arrive as pure inventory gains: `InventoryDiffProcessor` credits those gains as profit while the shop is open, and again via `wasLastClosedGroupOmnishop` for a purchase packet landing inside the close re-baseline window; losses still baseline away (points shops take no items). Standard coin shops (`SHOPMAIN`/`SHOPSIDE`) are not suppressed; they set a shop-open state that routes diffs to `ShopTracker`. Closing a shop does **not** schedule a re-baseline (unlike bank/GE): the shop branch advances the snapshot every tick, so a re-baseline would swallow the first post-shop diff. `SUPPRESSED_REGIONS` suppresses tracking by map region (`10588`, the PvP tutorial arena run by Pete Kayer at Ferox Enclave, plus other inventory-quarantine minigames): `updateSuppressedRegion` is re-evaluated per container event/game tick via `WorldView.getMapRegions()` (template ids, so instances match), both transitions schedule a re-baseline, exit opens a 3-tick suppression window (`onGameTick` ages it) since the loaner strip lands across several events/containers and a single-shot re-baseline is consumed by the first event, and `ActorDeath` is gated by `isTrackingSuppressed()` — covering the region, both exit-grace windows, and open suppressed interfaces — so staged deaths can't book a `"Death"` row while a loaner strip is still landing. Entries must be **instanced/isolated template regions only** — `getMapRegions()` returns every loaded region (~2-3 region halo), so a real overworld region would blind tracking for players merely nearby; those minigames use `MinigameQuarantine`'s HUD-visibility check instead. Region-set transitions are `log.debug`ged once per scene load ("Map regions: ...") so new ids can be captured in game. Storage interfaces that move items out of inventory without spending them are suppressed too: the Sailing boat cargo hold (`SAILING_BOAT_CARGOHOLD`/`_SIDE`) and the tool leprechaun's farming-tools store (`FARMING_TOOLS`/`_SIDE`) — deposits/withdrawals re-baseline instead of booking consumption or profit.
- `MinigameQuarantine.java`: Quarantine rules for minigames issuing temporary items. `MINIGAME_ONLY_ITEMS` is a denylist of item ids that cannot exist outside their minigame (Castle Wars supplies, Soul Wars supplies incl. worn team capes, Barbarian Assault eggs/horns/vials, GOTR cells, NMZ overload/absorption doses, Tithe seeds/fruit/fertiliser) — `CoinFlowPlugin.stripNonEconomicItems` removes them from raw gains/losses in `processInventoryChanges` (normal and re-baseline paths), `invItemsGainedThisTick`, and WORN diffs, so both grant and exit strip are invisible without needing any region data; persistent rewards (penance gear, CW tickets/cloaks, guardian essence) are excluded. `MINIGAME_HUD_COMPONENTS` (Tempoross + Gauntlet + LMS HUDs — each interface's `UNIVERSE`/`UNIVERSAL` component, looked up via the single-arg component `getWidget`) suppresses tracking while the HUD widget is visible: `CoinFlowPlugin.updateMinigameHudSuppression` latches visibility inside `updateSuppressedRegion` (per container event/tick — live `Widget.isHidden()`, never WidgetLoaded/Closed, so a loaded-but-hidden group can't wedge suppression on), transitions schedule a re-baseline, and close opens a 3-tick grace (`minigameHudGraceTicks`) for the trailing strip.
- `ConsumableRegistry.java`: Catalog of potions, foods, teleports, and degradation states with item IDs & dose rules. `isConsumable(id, name, itemManager)` classifies food/drink via `ItemComposition.getInventoryActions()` (`Eat`/`Drink`), falling back to name rules for potions, runes, ammo, and teleports. `isCrumblingJewelry(name)` identifies items that disappear on their last charge (last-charge `(1)` teleport jewelry: dueling, games, slayer ring, passage, burning, digsite, returning — plus castle wars bracelet — and single-life jewelry with no charge count: recoil, ring of life, binding, dodgy, slaughter, expeditious, forging, clay, chemistry). A worn removal of one is treated like fired ammo: routed to `pendingWornAmmoExpenses`, cancelled if it reaches INV, and expensed on `GameTick`. `isLastChargeTeleportJewelry(name)` is the narrower inventory-safe subset used by `ConsumablesAndDropsHandler` — recoil & friends are excluded there because an inventory loss usually means feeding a Ring of suffering, which `WeaponChargeTracker` expenses separately. Items that deplete to an uncharged variant (glory, wealth, combat bracelet, skills necklace, pharaoh's sceptre) are not in these sets; they pair as degradation instead. `isIgnoredName(name, ignoredSet)` is the shared ignored-items matcher: direct match, `canonicalIgnoreName` strips fractional suffixes (`" (dose)"`/`" (portion)"`), and `parsePotion` base names (so ignoring `"Prayer potion"` covers `"(1)"`–`"(4)"` and dose rows); `PotionDoseHandler`/`FoodPortionHandler` skip the expense when ignored but still reconcile diffs and drain GE basis, and `SessionApplier` filters ignored expenses **after** `repriceFromBasis` so basis lots never orphan. Synthetic `Death`/`GE Tax`/`Blast Furnace coffer`/`Barrows wear` rows are exempt by id (`CoinFlowSession.isSyntheticRowId`). `CoinFlowInputFilter.IGNORED_ITEMS` must keep `/` and `+` allowed — real item names contain them (`"2/3 cake"`, `"Dragon arrow(p++)"`). `isAmmo` covers cannonballs by name — `"Cannonball"` is the legacy name; since Sailing the dwarf-cannon ball is `"Steel cannonball"` and ship cannons fire bronze–dragon, chainshot and incendiary tiers.
- `WeaponChargeTracker.java`: Tracks supplies consumed inside charged weapons (tridents, blowpipe, bowfa, scythe of vitur, wildy chainmaces, etc.). Attack graphics/animations are the primary signal; `CHARGES_*_QUANTITY` varbit deltas are also polled each tick, converted to resource spend (blowpipe scales/darts, trident runes, crystal shards, revenant ether), and deduplicated against attack-triggered charges so a charge is never counted twice. Emitted as supply expenses on the game tick.
- `CannonTracker.java`: Dwarf multicannon bookkeeping. `InventoryDiffProcessor` calls `netDiff` on every inventory diff — including diffs about to be re-baselined, where a part gain would otherwise desync the ledger — but never while a shop is open (shop gains are purchases, not returns). Cannon-part losses without a Drop intent mark the cannon deployed (`deployedParts`, canonical `ItemID.TWPART1..4` + Leagues ornament parts); part gains net against it so pickup/Nulodion reclaim never books the kit as loot. Balls loaded while deployed (`ItemID.MCANNONBALL`, `GRANITE_CANNONBALL`) still flow through as ammo expenses, and balls returned on pickup/Empty strip the gain and emit `expenseReversals` capped at the loaded count (excess books as loot). `deployedParts` has no expiry and survives logout (the cannon does too — it is reclaimable); `loadedBalls` clears on transient resets since ball state on relog is unknown, and both clear on startUp/shutDown/session/account reset.
- `BlastFurnaceTracker.java`: Blast Furnace bookkeeping (see `reconciliation/BlastFurnaceHandler` for the diff-side half). Presence is detected from `BLAST_FURNACE_CONVEYER_BELT_CLICKABLE` `GameObjectSpawned`/`Despawned` events plus a one-shot `startUp` scene lookup (enabling the plugin while already at the furnace fires no spawn event); `GameState.LOADING` clears it, and a session/account reset keeps it (no spawn event re-fires while standing there). The coffer is a balance, not a spend: coin-only diffs are held aside by `holdCoins` and settled per tick in `GameTickProcessor` against the `BLAST_FURNACE_COFFER` varbit — an increase matched to a held loss is a deposit (no expense), a decrease matched to a held gain is a withdrawal (no profit), and any remaining decrease is drain at 12 gp/tick, **capped per tick since the last observed change** so a withdrawal swallowed by a re-baseline can never book as spend. A deposit racing a drain tick leaves a small held remainder (the coffer rose by less than the coins lost) — attributed to drain up to the same cap instead of expiring into a `Coins` spend. Drain accrues and charges the synthetic `"Blast Furnace coffer"` row (`ItemID.COINS_1000`, qty = gp, price = 1 — a coin-pile icon distinct from GE Tax's `COINS_10000`) in 1,200 gp batches, on leaving the furnace, and on leaving `LOGGED_IN` (`onLeftLoggedIn` flushes before the transient clear). Held coins unmatched after 2 ticks fall back: losses become `Coins` cash spends (e.g. the foreman fee), gains re-apply as income. The settle is intentionally NOT gated on bank-open (the drain keeps ticking while the bank chest is open) but is skipped on unsupported worlds and mid-death-settle. The dispenser-rescue ledger records `BLAST_FURNACE_*_BARS` varbit decreases so a bar collection swallowed by a re-baseline window (e.g. a coal-bag Open/Close toggle) is still credited with its recipe inputs — gated on an actual decrease within 3 ticks so bank-chest bar withdrawals are never rescued.
- `DeathTracker.java`: Tracks items lost on local-player death. `ActorDeath` captures combined inventory+equipment and **freezes all diff tracking** (INV, WORN, worn ammo, charge varbits) until post-respawn containers go quiet (~settle heuristic: min 3 ticks, 2 quiet ticks, 20-tick timeout). The settled loss (tradeables + coins only) is expensed to a synthetic `"Death"` row keyed by `ItemID.SKULL` (qty = gp, price = 1) like the `"GE Tax"` row, and each item is recorded in a recovery ledger at its death-time price. Recoveries reverse the row: reclaim interfaces (`GRAVESTONE_RETRIEVAL`, `GRAVESTONE_GENERIC`, `DEATH_OFFICE`) get an inv+worn baseline on open and are settled on `GameTick` once none remain open (scene loads can skip `WidgetClosed`); for 10 ticks after a settle, ledger-matching gains still count as recovery without a Take click (reclaimed items can arrive after the interface closes, where the post-close re-baseline would otherwise swallow them); a `"You ... retrieved ... your gravestone."` game message opens the same window — a direct gravestone claim delivers items by script with no interface and no Take click. Wilderness ground pickups reverse only when a matching Take click was recorded (`DeathTracker`'s own click list — `recentTakeClicks` is consumed by the open-bag pickup path). The reclaim fee is `max(observed inventory-coin loss ≤5m, chat fee ?? computed fee)`: the `Death charges you X coins.` message is the exact charge and is preferred over the computed schedule estimate (the game's reclaim valuation differs from our prices), while the computed fee uses official schedules on the recovered items' ledger prices — Death's Office 5%/unit ≥100k, gravestone tiers 1k/10k/100k per unit by value (500k combined cap), 50% off for iron accounts except ultimate ironmen — and the `Death charges you X coins.` game message covers bank/coffer payments even when the reclaimed item never enters inv/worn (reclaim-to-bank on a full inventory); a chat fee that outlives its settle applies deferred after 2 ticks. Lost session gains are `markConsumed` and restored via `CoinFlowSession.withRestoredConsumption`. The ledger survives logout/transient resets (reclaim often happens after a relog); it clears only on startup/shutdown/session reset. Limitations: reclaim-to-bank items reverse only if a later gain matches the ledger, untradeable value is untracked, content-specific fee discounts (e.g. 75% off new boss deaths) aren't modeled, and reclaim interfaces not in the set are untracked.
- `GrandExchangeTracker.java`: Settles GE buy/sell fills from `GrandExchangeOfferChanged` events (independent of suppressed inventory diffs). Buy fills only record FIFO cost basis; sell fills decompose by carried value — GE basis (real margin), session tracked gains (estimate correction), or the gross fill price for untracked stock (records only the GE tax). The `untrackedSalesAsIncome` config instead carries untracked stock at zero so proceeds surface as income; it applies to both GE and shop sells. `repriceFromBasis` runs on every supply-expense batch in `CoinFlowPlugin.processGainsLossesAndExpenses` so consumed items bought this session (GE or shop) are charged at actual purchase cost and their basis lots are drained rather than orphaned. Dose/portion expenses (`PotionDoseHandler`, `FoodPortionHandler`) register via `ReconciliationContext.addFractionalSupplyExpense` and are excluded, since their quantity is in sub-units and would over-drain whole-item basis. `transferSetExchangeBasis` runs on the suppressed inventory diff while the clerk's item-sets exchange is open, or on a diff landing within 3 ticks after close (`wasLastClosedGroupItemsets` is age-bounded so a stale close cannot arm a later re-baseline window). One-sided diffs participate unconditionally — a conversion split across container events stashes the consumed side's basis (`pendingSetExchangeCost`, ≤5 ticks) or remembers the produced items (`pendingSetExchangeGains`) so the late half attaches retroactively (basis is keyed by item id). When a `... set` item is among the losses, only set-item basis is consumed; otherwise all non-coin losses count as conversion inputs. Basis is re-attached to the produced side pro-rata by market value, so unpacked components sell at the true margin against the set's purchase cost. Collections remain re-baselined so proceeds are never double counted. `EMPTY` events are a login flood unless the client is `LOGGED_IN`, in which case they are a genuine slot clear. Observations are seeded from `client.getGrandExchangeOffers()` on startUp/reset.
- `GrandExchangeTax.java`: `GrandExchangeOffer.getSpent()` is **gross (pre-tax)** for sells. Net proceeds = gross − per-item tax (2%, floored, capped 5m/item, exempt-item list). Tax on untracked sells surfaces as its own `"GE Tax"` expense row keyed by `ItemID.COINS_10000` (coins-pile icon) so it isn't blended into the generic "Coins" row; tax embedded in tracked/basis residuals stays folded into those residuals since it can't be separated from price drift.
- `ItemPricing.java`: Shared item valuation (`priceOf`): GE price → fixed coin/platinum → HA fallback for untradeables, used by all gain/supply-expense valuation sites (gains, worn ammo, charge resources, consumable/drop expenses, processing inputs). `UNALCHABLE_UNTRADEABLES` (blessed bone shards, blessed bone statuettes) are untradeable *and* unalchable — every composition carries a nominal `getHaPrice()` even when the item cannot be alchemised, so the HA fallback would book phantom profit/spend. `isValueless` strips them from diffs alongside minigame-only items in `stripNonEconomicItems` (fully invisible: no row, no gain, no spend); `priceOf` also returns 0 for them as a safety net on paths that bypass the strip. Only add verified-unalchable items — wrongly listing an alchable loses its value twice (0 at pickup, ~0 alch margin since the basis self-references). The `trackUntradeableItems` config (default off) additionally strips `isUnpricedUntradeable` items (untradeable + no market price, i.e. the whole HA-fallback population) while off — cash-basis accounting: invisible while held, and since the item loss never reaches `HighAlchemyHandler`, a later alch books the coins as plain income (+HA − nature rune), the same lifetime total as accrual without the ±HA gross churn. The toggle is not retroactive: items gained while off stay untracked, and items gained while on remain booked at HA even if their later loss lands while off (a brief phantom-profit window is accepted).
- `ShopTracker.java`: Reconciles inventory diffs while a standard coin shop is open — the coins delta is the actual price. Buys record FIFO cost basis in `GrandExchangeTracker`'s shared pool (asset conversion) — except untradeable buys (`!isTradeable()`), which are expensed at cost since the cash can never be recovered; sells settle via `settleShopSell` (no tax) against carried value: basis (real margin) → session tracked gains (estimate correction) → untracked stock carried at sale price (net zero, or carried at zero as income when `untrackedSalesAsIncome` is enabled). Non-coin diffs (tokkul/points shops, noise) are suppressed. NPC **dialogue** purchases (Zaff's staffs, Ali Morrisane, etc.) open no shop interface; `CoinFlowPlugin.isCoinsOnlyPurchase` detects the "coins are the only loss, non-coin items gained" diff shape in the normal pipeline and routes it through `ShopTracker` too, so cash spent does not vanish while the goods are counted as loot.
- `CoinFlowInputFilter.java`: Filters chatbox/menu inputs and validates triggers.

### Reconciliation Engine (`src/main/java/com/coinflow/reconciliation/`)
- `ReconciliationHandler.java`: Handler interface (`boolean handle(ReconciliationContext context)`).
- `ReconciliationContext.java`: Context DTO passing snapshots, item diffs, and client metadata down the chain.
- `InventoryReconciliationEngine.java`: Orchestrator running diffs through prioritized handlers until reconciled.
- `BlastFurnaceHandler.java`: Blast Furnace diff reconciliation, active only while `ReconciliationContext.blastFurnaceActive` (set per-diff from `BlastFurnaceTracker.isActive()`); ordered right after `DroppedItemPickupHandler` so own-drop pickups resolve first and it runs before `ProcessingHandler`/`ConsumablesAndDropsHandler`. Unnoted recipe ore/coal losses with no Drop intent are stripped as belt loads (free inputs) and matching session gains are retired via `context.retireSessionGain` — the cost is deferred: unnoted recipe-bar gains are charged the half-coal Blast Furnace recipe (`RECIPES`) as supply expenses, repriced through `repriceFromBasis` downstream. A diff with BOTH a recipe-input loss and a recipe-bar gain is a Superheat smelt or a same-tick load+collect — the handler steps aside entirely so `ProcessingHandler`'s full-coal smelting rule owns it. Ignored bars charge no inputs (net can never go negative on a filtered row); ignored inputs are skipped individually. Perfect gold is excluded (untradeable). `DISPENSER_VARBIT_TO_BAR` maps the 10 dispenser varbits for `BlastFurnaceTracker`'s rescue ledger.
- `PotionDoseHandler.java`: Reconciles multi-dose potions (4->3->2->1 dose, empty vial creation).
- `FoodPortionHandler.java`: Reconciles multi-bite foods (pies, pizzas, cakes) and single-bite meals.
- `ConsumablesAndDropsHandler.java`: Reconciles ground drops, monster loot, and single-use consumables. Residual coin/platinum losses that survive the specialist handlers are cash spends (fees, fares, coffers) expensed at face value and retire matching session coin gains (like consumables) — they never enter drop bookkeeping, which would otherwise suppress later coin pickups. A coin loss paired with a Barrows repair in the same diff is absorbed up to `barrowsRepairAllowanceGp` (wear was expensed as it accrued — the fee is a recharge, not a new spend; only the excess is a cash spend, and a fee landing in a separate diff falls back to one). Absorbed gp also retires the matching base's entry in `barrowsWearBookedByPiece` so booked wear is never absorbed twice. Intentional coin drops (Drop-intent) keep the own-drop path. Banker coin<->platinum exchanges (1:1000) are netted out first; `isCoinsOnlyPurchase` ignores platinum-only gains so exchanges aren't treated as purchases. A loss carrying an `openIntentIds` flag (a CC_OP `Open`/`Loot`/`Search` click on the item — caskets, impling jars, supply crates) is expensed as a consumed supply; `repriceFromBasis` then charges carried purchase basis, so a bought pack is charged at cost and the loss never enters drop bookkeeping (where it would suppress a later genuine pickup). Object/world `Open` clicks are GAME_OBJECT actions and mint no intent. Last-charge teleport jewelry (`isLastChargeTeleportJewelry`) is expensed like a consumable — it crumbles when rubbed from the pack — but only inside the `!dropIntent` guard. Unexplained one-sided losses while a skill is active are expensed via `ConsumableRegistry.isSkillSink` — items consumed purely for XP with no realizable output: Prayer bones/ashes/ensouled heads, Firemaking logs, Farming seeds/compost, Construction planks/nails/bagged items, Runecraft essence, Hunter logs/seeds/meat/bait, and Herblore herbs (the Mixology refiner's paste gain is stripped untradeable first, leaving a one-sided loss — two-sided diffs like potion-making are claimed by `ProcessingHandler` earlier and never reach this check).
- `ChargeDegradationHandler.java`: Reconciles charge/degrade-state changes on the same item in both directions: usage degradation (Barrows 100->75->50->25->0, jewelry (n)->(n-1)), depletion to uncharged, recharges ((n)->(m), uncharged->(m)), Barrows repairs ("X 50" -> "X"), and first-use init ("X" -> "X 100"). Item sides cancel; any coin fee is left for the cash-spend path, except a staged Barrows piece returning to its bare name arms a repair-fee allowance on the context (`repairAllowanceGp` = the most wear that stage could represent, capped at the gp actually booked against that piece in `CoinFlowPlugin.barrowsWearBookedByPiece` — gear degraded before the session pays its repair as a normal cash spend) so the paired fee is absorbed. Single-step usage transitions (`isUsageStepPair`) are preferred over broad recharge/repair matches so same-base loot in the same tick survives; Drop-intent losses are never paired; the bare-name Barrows direction is limited to the six brothers' gear. Imbue conversions (`X`/`X (e)`/`X (r)` ↔ `X (i)`/`(ei)`/`(ri)` — NMZ, Soul Wars, Emir's Arena) pair by shared base name since imbued items are untradeable and never drops; the un-imbued side may itself carry `(e)`/`(r)` (Salve amulet(e), Ring of suffering (r)), so both sides are reduced to the base before comparing. Unmatched `(i)`/`(ei)`/`(ri)` gains are also suppressed from `rawGains` for split-tick conversions, alongside partially degraded items and lit light sources.
- `BarrowsWear.java`: Barrows degradation accounting — wear is the spend, repairs are recharges. Only stage transitions are visible (each piece is 1000 hidden points: bare->100 = 1 pt, 100->75 = 249, then 250 per stage, summing to the full NPC repair cost); NPC rates per point are weapon 100 / body 90 / legs 80 / helm 60 (armour-stand Smithing discount not modelled). `InventoryDiffProcessor`'s WORN pairing queues a downward step's gp into `pendingBarrowsWear` (skipped when the piece's bare name is ignored); `GameTickProcessor` books it on the synthetic `"Barrows wear"` row (`ItemID.BARROWS_INTERFACE_DHAROK`, qty = gp, price = 1) under the worn-ammo gate. Because a worn degrade between two same-base copies is indistinguishable from swapping spares, a same-tick INV diff showing the piece move UP a stage marks `barrowsSwapBasesThisTick` (computed on the raw diff before `GearSwapHandler` cancels it) and the flush vetoes that base; an INV-side downward step without a worn counterpart books nothing. Each flush merges the charged gp into `barrowsWearBookedByPiece` (base -> session wear), the ledger `ChargeDegradationHandler` caps repair absorption against and `consumeBarrowsRepairAllowance` retires from; it clears only on session/account reset since the wear rows live in the session.
- `GearSwapHandler.java`: Reconciles inventory <-> equipment swaps (net 0 GP change).
- `HighAlchemyHandler.java`: Reconciles High/Low Alchemy casts (alched item + runes consumed -> coins added).
- `DroppedItemPickupHandler.java`: Distinguishes picking up player's own dropped items vs newly spawned ground items.
- Drop vs. consume: an inventory loss alone cannot tell a drink from a drop. `CoinFlowPlugin` records `MenuOptionClicked` "Drop" clicks (`recentDropIntents`, 2-tick window) and flags matching losses on `ReconciliationContext.dropIntentIds`. `PotionDoseHandler` and `ConsumablesAndDropsHandler` route flagged losses through the own-drop path (session deduction or `recentlyDroppedOwnedItems`) instead of expensing them, so a drop/pickup round trip nets to zero on both gross and spent. Pack opens are the mirror image: `recentOpenIntents` (3-tick window, CC_OP-only, non-container targets) flags losses on `ReconciliationContext.openIntentIds` so they expense instead of dropping.
- Count Drops as Spent (`countDropsAsSpent`, requires `trackSpent`; `ReconciliationContext.isDropsAsSpent()`): opt-in alternative where a **drop-intent** loss is charged as a supply expense at market price (`addDropExpense`, tracked in `recentlyExpensedDrops`) and the matching session gain is marked consumed. Only click-confirmed drops qualify, so unexplained losses (quest hand-ins, Destroy, death) keep the legacy path. On pickup, `DroppedItemPickupHandler` removes the gain from `rawGains` and emits `expenseReversals`; `CoinFlowSession.withExpenseReversal` reduces the expense row proportionally and restores the gain's `remainingQuantity` (`TrackedItem.withRestoredConsumption`), so a round trip leaves the session exactly as before. Drop expenses are excluded from GE basis repricing (`getBasisExcludedExpenseIds`) so a pickup never orphans a basis lot. Pickup matching is keyed on the pending map, not config, so flipping the toggle mid-session is safe. The reversal must be included in the post-reconcile trigger condition in `CoinFlowPlugin.onItemContainerChanged`, since a pickup-only tick leaves `rawGains` empty — as must `consumedSessionQuantities`, since a fully absorbed Barrows repair fee produces no gains/expenses/reversals but still retires session coin gains.
- `ItemNotingHandler.java`: Reconciles noting and unnoting items (Tool Leprechaun, Phials, Piles), matching unnoted <-> noted swaps and recording service fees.
- `ProcessingHandler.java`: Reconciles production skilling (inputs consumed ➔ products created).
- `ProcessingPatternRegistry.java`: Recipe lookup mapping skilling inputs to outputs (crafting, fletching, cooking, etc.). Smithing matches `"Steel cannonball"` (4 per steel bar — the post-Sailing name; the legacy `"cannonball"` name is kept too) plus the Sailing ship-cannonball tiers.

## Logging

- Use `log.debug()` for developer/diagnostic logging.
- Do not use `log.info` for per-frame or per-event logging - RuneLite runs at INFO level in production, so high-frequency info logs will pollute user logs. `log.info()` is fine for one-time startup/shutdown messages or infrequent events.

## Threading & Concurrency

- Never use `Thread.sleep()`.
- Never block on `shutDown()` or `startUp()` — don't call `executor.awaitTermination()` in shutdown, just use `shutdownNow()`.
- Never do blocking network IO or disk IO on the client thread. The OkHttp thread pool can be used for blocking network requests.
  If you need to call back into `client` from the okhttp threadpool, such as from the response queued with `enqueue()`, use `clientThread.invoke()`
- Explicitly cancel scheduled tasks (e.g. `ScheduledFuture`) on shutdown, in addition to shutting down the executor.
- For batching async work, use `CompletableFuture.allOf()` — not `CountDownLatch`.
- If you must use `Process.waitFor()`, always pass a reasonable timeout.

## Performance

- Don't scan the entire scene every tick or frame. Use events such as object and npc (de)spawn to track what you care about and maintain your own collection.
- Keep the computations in Overlays, which are run each frame, to a minimum.

## API Usage

- Use `net.runelite.api.gameval` package constants — `ItemID`, `InterfaceID`, `ObjectID`, etc. Never hardcode magic numbers when gameval constants can be used instead.
- Use `LinkBrowser` to open URLs, not `java.awt.Desktop`
- When looking up Widgets, pass the component ID from gamevals (eg `client.getWidget(InterfaceID.DomEndLevelUi.LOOT_VALUE)`) - do not manually combine interface + component child IDs.
- Use of Java reflection is forbidden.

## HTTP & JSON

- Use OkHttp for all HTTP requests. `@Inject OkHttpClient` to get the HTTP client. Do not use `HttpURLConnection`, `java.net.http.HttpClient`, or Apache HttpClient.
- Use `@Inject Gson` to get a Gson instead, never create your own from scratch. You can use `.newBuilder()` to create one derived from the base `Gson.`
- Do not add transitive dependencies from `runelite-client` directly to `build.gradle`, such as gson, guice, or okhttp.
- Never execute okhttp calls on the client thread. Prefer using `enqueue()` which places the request on the okhttp threadpool.

## File I/O

- All file i/o must go through the Filepath utility. Use of Filepath requires setting PluginDescriptor `internalName` to the internal name of the plugin.
- Use `Filepath.Chooser` instead of `JFileChooser`
- To migrate a legacy plugin data folder from .runelite automatically, set PluginDescriptor `legacyDataDirectory` to the name of the legacy folder.

## Config

- Config group names must be specific — e.g. `"deadman-prices"`, not `"deadman"`.
- Never rename a config key or config group without providing a migration. Renaming silently resets users' saved settings.
- If you add a `@ConfigItem` that toggles a feature involving a third-party server, it must:
  - Be **disabled by default** (opt-in)
  - Have a `warning` field set to: `"This feature submits your IP address to a 3rd-party server not controlled or verified by RuneLite developers"`

## Plugin Setup & Packaging

- Rename everything from the template. Do not leave `com.example`, `ExamplePlugin`, `ExampleConfig`, or `example` as the config group. Rename the package path, class names, config group, `build.gradle` group, `settings.gradle` project name, and `runelite-plugin.properties`.
- Do not include a `META-INF/services/net.runelite.client.plugins.Plugin` file.
- Do not commit build artifacts — no `.class` files, `out/` directories, or `.tmp` directories.
- `build.gradle` must target Java 11** and match the structure of the example-plugin template.
- Retain a permissive license, such as BSD-2.

## Resources & Assets

- Optimize icon PNGs. Java loads images at full resolution in memory (`width × height × 4` bytes), so a seemingly small file can use significant memory.
- Ensure PNGs are actually PNGs — do not rename JPEGs or ICOs to `.png`.

## Cleanup

- Remove unused config classes, fields, and imports.
- Clean up subscriptions, listeners, and overlays in `shutDown()`.
- Do not mix code reformatting with feature changes in the same commit — it makes diffs unreadable for reviewers.

## Testing

You cannot verify plugin behavior yourself. Even if you have screen-capture or computer-use tools available, **do not use them to interact with RuneScape** — automating game input violates Jagex's third-party client guidelines and will get the user's account banned. Only the user can confirm a plugin works in-game.

After completing a task, do not declare it done. Instead:

1. Offer to launch RuneLite for the user by running `./gradlew run` from the plugin's root directory.
2. Instruct the user to follow the "Using Jagex Accounts" instructions found at https://github.com/runelite/runelite/wiki/Using-Jagex-Accounts to login to the development client.
3. Tell the user *what to test* — the specific behavior you changed, the golden path, and any edge cases worth exercising.
4. Wait for the user to confirm the feature works in-game before considering the task complete. A clean JVM start is not a passing test.

# Releasing to the Plugin Hub

This plugin is published as an external hub plugin: `runelite/plugin-hub` holds a manifest (`plugins/coinflow`) that points at a commit in this repo. A release = merge the feature, bump the version, move the manifest pointer, PR the hub.

1. **Merge the feature PR** to `main`; pull local `main` to the merge commit.
2. **Bump `version=`** in `runelite-plugin.properties` (semver; features → minor), commit directly to `main`, push. A version bump is a docs-scale change — it does not need its own PR.
3. **Sync the fork**: `stillworld/plugin-hub` `master` must be fast-forwarded to `runelite/plugin-hub` `master`.
4. **Branch the fork** (e.g. `coinflow-<version>`), update `plugins/coinflow`:
   ```
   repository=https://github.com/stillworld/coinflow.git
   commit=<full SHA of the version-bump commit on main>
   ```
5. **Open the PR** `stillworld:<branch>` → `runelite:master` with a short "what's new" list. Hub CI rebuilds the plugin from that commit; watch `package-plugin` for failures. Review takes days; a stale fork or a commit that isn't on `main` are the usual rejections.

`gh` is not installed on this machine — the API path that works (token lives in the osxkeychain git credential):

```bash
TOKEN=$(printf "protocol=https\nhost=github.com\n\n" | git credential fill | grep "^password=" | cut -d= -f2-)
# Sync fork
curl -X POST -H "Authorization: Bearer $TOKEN" \
  https://api.github.com/repos/stillworld/plugin-hub/merge-upstream -d '{"branch":"master"}'
# Branch off fork master
curl -X POST -H "Authorization: Bearer $TOKEN" \
  https://api.github.com/repos/stillworld/plugin-hub/git/refs \
  -d '{"ref":"refs/heads/coinflow-X.Y.Z","sha":"<fork master sha>"}'
# Update manifest (needs the file's current blob sha on the branch)
curl -X PUT -H "Authorization: Bearer $TOKEN" \
  https://api.github.com/repos/stillworld/plugin-hub/contents/plugins/coinflow \
  -d '{"message":"Update coinflow to X.Y.Z","content":"<base64 manifest>","sha":"<file sha>","branch":"coinflow-X.Y.Z"}'
# Open PR
curl -X POST -H "Authorization: Bearer $TOKEN" \
  https://api.github.com/repos/runelite/plugin-hub/pulls \
  -d '{"title":"Update coinflow to X.Y.Z","head":"stillworld:coinflow-X.Y.Z","base":"master","body":"..."}'
```

# Plugin Rules & Restrictions

Features that are **forbidden or restricted** in RuneLite hub plugins.
Sourced from [Jagex's Third-Party Client Guidelines](https://secure.runescape.com/m=news/third-party-client-guidelines?oldschool=1) and RuneLite's [Rejected or Rolled-Back Features](https://github.com/runelite/runelite/wiki/Rejected-or-Rolled-Back-Features).

**If your plugin does any of the things listed below, it will be rejected.**

## Forbidden Language Features

- All code must be Java 11 compatible
- No use of reflection
- No use of JNI or JNA
- No direct access to native memory access via Unsafe or LWJGL
- No executing external processes, including with Process or ProcessBuilder
- No downloading or dynamic loading of code, including classloading
- No runtime generation of code
- No use of Java (de)serialization

## Boss & Combat Restrictions

Applies to all bosses, Raids sub-bosses, Slayer bosses, Demi-bosses, and wave-based minigames (Fight Caves, Inferno, etc.):

- No next-attack prediction (timing or attack style)
- No projectile target/landing indicators
- No prayer switching indicators
- No attack counters
- No automatic indicators showing where to stand or not stand (manual tile marking is allowed)
- No additional visual or audio indicators of a boss mechanic, unless it is a manually triggered external helper
- No advance warning of future hazards (highlighting currently active hazards is OK)
- No "flinch" timing helpers
- No combat prayer recommendations
- No NPC focus identification (which player the NPC is targeting)
- No content simulation (e.g. boss fight simulators)

New high-end PvM boss plugins are not accepted as a blanket policy.

## PvP Restrictions

- No removing or deprioritising attack/cast options in PvP
- No opponent freeze duration indicators
- No PvP clan opponent identification
- No PvP loot drop previews
- No identifying an opponent's opponent
- No PvP target scouting information
- No player group summaries (attackable counts, prayer usage, etc.)
- No level-based PvP player indicators (highlighting attackable players or those within level range)
- No spell targeting simplification (removing menu options to make targeting easier)

## Menu Restrictions

- No adding new menu entries that cause actions to be sent to the server
- No conditional menu entry removal based on NPC type, friend status, etc. (can be overpowered)

## Interface Restrictions

- No unhiding hidden interface components (special attack bar, minimap)
- No moving or resizing click zones for 3D components
- No moving or resizing click zones for combat options, inventory, equipment, or spellbook
- No resizing prayer book click zones
- No resizing spellbook components
- No removing inventory pane background or making it click-through
- No detached camera world interaction (interacting with the game world from a camera position that isn't the player's)

## Input Restrictions

- No injecting input events, including mouse and keyboard events
- No autotyping — plugins must not programmatically insert text into the chatbox input (includes pasting, shorthand expansion)
- No modifying outgoing chat messages after the user sends them

## Data & Privacy Restrictions

- No exposing player information over HTTP
- No crowdsourcing data about other players (locations, gear, names, etc.)
- No credential manager plugins that stores account credentials

## Content Restrictions

- No adult or overtly sexual content
- No plugins that use player-provided IDs for their entire functionality (causes moderation issues)
